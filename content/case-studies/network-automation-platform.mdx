## Architecture

NetBox became the single source of truth for devices, interfaces, IP addresses and VLANs. Every configuration is rendered from NetBox data through Jinja2 templates, so the network can never disagree with the documentation.

### The pipeline

A change starts as a merge request that edits NetBox data or a template. GitLab CI then:

1. Renders the candidate configs for every affected device
2. Lints them with Batfish and custom policy checks
3. Posts a device-by-device diff as a merge request comment
4. After approval, deploys in batches with pre- and post-checks

```yaml
deploy:
  stage: deploy
  script:
    - nornir-run precheck --limit "$CHANGED_DEVICES"
    - ansible-playbook deploy.yml --limit "$CHANGED_DEVICES" --forks 20
    - nornir-run postcheck --limit "$CHANGED_DEVICES" || ansible-playbook rollback.yml
  when: manual
  environment: production
```

### Rollout strategy

Changes go out in waves: one canary device, then 10%, then the rest. If a post-check fails (a BGP session down, an interface error counter climbing), the batch rolls back automatically and the pipeline stops.

| Wave | Devices | Checks | Auto-rollback |
|------|---------|--------|---------------|
| Canary | 1 | BGP, interfaces, reachability | Yes |
| Early | 10% | Same, plus traffic baseline | Yes |
| Full | Remaining | Same | Yes |

### Key decisions and trade-offs

1. **NetBox over spreadsheets and a custom CMDB**: NetBox's API and plugin ecosystem meant we spent our time on automation, not on building an inventory tool.

2. **Nornir for checks, Ansible for pushes**: Ansible's modules made config deployment simple for the whole team, while Nornir's plain-Python model made complex validation logic easier to write and test.

3. **Batfish in CI**: Offline analysis catches routing loops, ACL mistakes and unreachable prefixes before a single device is touched. It added two minutes to every pipeline and prevented several outages in the first month.

## Adoption

Tooling alone doesn't change how a team works. I ran weekly pairing sessions, wrote runbooks for the common change types, and kept an escape hatch for emergencies so nobody felt trapped by the new process.

### Results

Within six months, 94% of network changes went through the pipeline. The remaining 6% were emergency changes, which were then codified after the fact.
